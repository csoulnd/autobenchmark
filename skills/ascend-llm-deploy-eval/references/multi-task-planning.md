# 多模型、多部署与多 case 的 Agent 规划

仅在需求包含多个模型、部署或 case 时读取；简单任务沿用主流程，不向用户讲解内部调度结构。

## 从需求形成清单

按模型 → 部署形式 → 负载组合整理矩阵。复用已有服务器、权重、镜像和脚本事实；明确的组合直接标准化，仅询问会改变范围的歧义。“全部配置”以提供目录中实际识别出的部署形式为依据，不臆造额外组合。请求数、轮数等默认值写入计划，不作为待确认项。需要用户审阅时只展示部署、负载、服务器分配和实际阻塞，不逐 case 展开执行命令。

## 独立服务器上的单机任务

Agent 将独立单机部署分配到互不重叠的服务器，生成各自的 job_spec；使用 [整组执行](group-execution.md) 一次提交整组计划。主节点宿主机的 group_run.py 自动启动可并行任务并等待依赖；每个任务仍使用现有串行执行器。这不是同一 job_spec 中 phase_id 的并行能力；多 P/D 拓扑仍需单独适配。

- 并发组之间服务器资源必须互不重叠；当前不规划同机不同卡的并发任务。分别完成预检，确认没有未授权占用；提交时再次核验即时资源。
- 每个独立任务使用唯一 job_id、任务目录、容器归属和监控记录。一个服务器上的多个模型/部署优先纳入同一个串行任务，以便复用兼容容器。不要把相同 case 自动复制到每台服务器，除非用户要求重复对比。
- 将原始需求、拆分后的任务、对应 case、主机分配、依赖与状态保存在仓库外的 Agent 规划记录中，不向当前 Schema 增加未实现的调度字段。拆分不改变负载、部署参数或测试次数。

## 单机任务之后的双机任务

需要复用两台机器的双机部署必须等待两侧前置任务终止且任务级释放核验完成，再重新检查现场资源并启动。前置 case 的 record_only 失败本身不等于依赖资源不可用；清理失败、归属未知或仍有任务运行则阻塞后继。仅观察到进程退出不能越过此条件。

后继提交由远端整组协调进程完成，不等待 Agent 下次唤醒。监控继续只读；协调器不会修改负载、部署参数或终止未知资源。所有子任务必须先完成有人值守预检，冻结计划和脚本快照；未适配的部署不得混入可执行清单。

## 汇总与披露

监控按各独立 job_id 读取证据并去重；整组报告覆盖所有任务、每个 case 和清理结果。正常运行不发送重复进度。能力缺口、上下文长度冲突、参数变更等只在与当前请求相关时提出；不要求用户将这些检查事项写进任务提示词。多个任务并发提交尚未现场验证时，如实区分“已规划”和“已验证”。
