# 实施决策与开发流程

更新日期：2026-10-29

本文记录讨论确认的首版开发范围和实施顺序。与 `design.md` 原方案不同的首版安排，以本文为准；原方案保留为后续扩展参考，不代表当前已实现能力。

## 1. 首版目标与限制

首先完成一个确定性测试任务的 Skill 开发，形成首版本 Skill 和脚本，并完成确定场景下的性能测试闭环。

- 假设部署过程无异常，首版聚焦正常执行路径；异常处理和恢复机制暂不作为本轮开发重点。
- 模型权重、容器镜像、测试工具默认已准备完毕，不在首版实现下载、安装或准备流程。
- 优先完成性能测试，精度测试后续再扩展。
- 冒烟测试暂采用单条真实推理请求，具体请求及通过判据在手工验证时确定。
- 固定测试场景，先验证该场景可执行、可复现，再提炼可复用配置与 Reference。
- 首版本 Agent 执行模式为 `plan - test`，计划前多轮对话补齐必要信息，计划后由 Agent 根据脚本反馈持续驱动执行；具体交接字段留待轨迹验证。

上述假设是本轮范围约束，不代表异常处理、环境准备或生产验收已经完成。

## 2. 开发与验证顺序

### 第一步：手工验证确定场景

先手工完成推理服务拉起、单条推理请求冒烟测试和性能测试。记录实际使用的环境、命令、配置、输入、输出及耗时，形成能够交给 Agent 执行的任务基线。

### 第二步：编写首版 Skill 和脚本，交给 Agent 执行一次

根据手工验证的有效步骤编写首版 Skill 和脚本。由 Agent 按 `plan - test` 模式执行一次完整任务，保留执行轨迹、阶段输入输出和时延记录。

### 第三步：从执行轨迹提取完整流程并人工调整

Agent 执行完成后，以实际轨迹为依据提取流程，由人工审阅和调整，分别设计：

- 询问阶段的提示词：明确需要询问、确认和补全的信息。
- 阶段交接的结构化 JSON：明确任务参数、上下文和执行所需信息。
- 各执行阶段的脚本：将已经验证的确定性操作固化。
- 输出的结构化形式：明确执行结果、性能结果、产物与时延的表达。

此阶段先依据真实任务提炼契约，不提前将原方案的全部字段与机制作为首版实现要求。

### 第四步：强弱 Agent / Model 复现与稳定性验证

准备强、弱两类 Agent / Model 组合，尤其使用能力较弱的组合复现同一个测试任务。比较完成情况、执行轨迹、输出及耗时，确认任务的稳定性。具体组合、重复次数和稳定性判据在后续讨论中确定。

### 第五步：依据实际任务组织配置与 Reference

根据手工验证、Agent 执行、人工调整及复现测试中实际使用的配置，确定 Reference 的组织形式。区分固定流程、场景配置和验证证据，避免提前构建未经真实任务验证的通用配方体系。

## 3. 过程记录要求

从手工验证开始，到 Agent 首次执行、人工调整及强弱组合复现，均保留可追溯记录。

- 记录各阶段开始、结束和耗时，以及端到端耗时。
- 区分流程执行时延与性能测试工具输出的推理性能指标。
- 记录执行者或 Agent / Model 组合、任务输入、实际配置、命令或脚本、输出和产物位置。
- 保留 Agent 执行轨迹与人工调整内容，用于流程提取和复现比较。

字段名称、时间口径和结构化输出 Schema 在后续设计时确定。

## 4. 当前代码状态

当前仓库仅包含目录框架、五个脚本入口、结构化阻止返回及独立复制执行测试。任务 Schema 尚为拒绝所有输入的占位定义；实际部署、测评、生产编排和资源清理尚未实现。

保留现有五脚本职责划分：plan_run 校验并生成计划，preflight 检查环境与资源，deploy 拉起服务并完成单请求冒烟，evaluate 执行性能测试，finalize 汇总归档并按约定清理。原方案 AC-01 至 AC-18 的完整生产验收仍未完成。

## 5. Agent 与脚本的职责共识

计划前由 Agent 多轮询问、查询环境、复用已有信息；信息齐备后再调用 plan_run 形成计划。脚本折叠各阶段内的操作，以减少工具调用和会话轮次，不替代模型判断。Agent 读取各脚本的结构化结果、耗时和异常证据，决定下一步；关键计划变更记录原因，超出确认范围时再询问用户。

正常路径按五脚本顺序推进，复杂异常交由 Agent 诊断。正常完成或中止均应进入 finalize，保留幂等与任务资源归属要求；Agent 调用不能保证语言级 finally 的执行语义，进程中断兜底后续设计。首版假设正常部署，不等于完整异常处理已经实现。

复现过程同时记录工具调用次数和会话轮次。Reference 组织依据实际任务提炼，开发期候选配置不得冒充已验证配方。

## 6. 后续设计讨论事项

- 确定首个测试场景的硬件、驱动、CANN、vLLM-Ascend / vLLM 版本、模型及镜像。
- 确定性能测试工具入口、负载配置、指标口径与结果判据。
- AISBench 运行位置作为环境配置记录，宿主机或容器均可，沿用手工验证方式，不作为阻塞项。
- 确定 `plan - test` 的阶段边界、询问提示词、交接 JSON、脚本职责及结构化输出。
- 确定单条推理冒烟请求与通过判据。
- 确定时延记录口径、强弱 Agent / Model 组合、复现次数和稳定性判据。
- 依据实际测试任务确定配置与 Reference 的组织形式。

本次仅更新实施决策，暂不修改脚本或开展真实环境测试。

## 2026-10-30：结构化规划契约落地
