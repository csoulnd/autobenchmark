# 配置入库规则

## 目录与命名

使用 `模型/部署方案/配置/`。部署方案例如 `single-pd-mix`、`single-pd-split-1p1d`、`double-pd-split-3p1d`；single/double 表示物理机器数，不设置硬件类别。每个配置独立保存，不把变体嵌套在另一个配置里面。

配置名称突出差异，例如 `p-dp2-tp2_d-dp4-tp1_mooncake-hybrid` 或 `eplb-20261104`。不要以实际 IP、机器编号或端口作为配置身份。

## 配置文件

- `p.sh`、`p1.sh`、`d.sh` 或 `mixed.sh/start.sh`：实际服务参考命令。
- `proxy.sh`：PD 代理启动命令；根据服务脚本的 HTTP 端点配置。workers/重试等显式保存，不擅自推断。
- `env.sh` 与扩展源码：确有依赖才保存，记录来源。
- `NOTES.md`：统一说明入口，按下方模板填写。
- 原有 `NOTES.txt`：历史原始记录，不再追加新规范内容。

不添加证书、硬件矩阵、无关账号等字段。原有 LICENSE 为第三方源码授权文件，应保留。

## 入库过程

1. 保存用户提供的完整脚本及必要依赖，不以官方命令替换用户命令。
2. 提取实例、DP/TP/PCP、connector、代理 HTTP 端点、环境变量和现场绑定项。
3. 根据目标版本社区规范检查 Shell/JSON、冲突参数、缺失变量和 P/D 一致性；版本不明时标为待核验，不凭当前 main 判错。
4. 明确区分错误、版本疑点与可替换的现场值；命令修改须有可审阅差异。
5. 更新 `catalog.json`、总 `INDEX.md` 和模型 `INDEX.md`。catalog 仅为索引，不是可执行 job_spec，不宣称是完整命令解析结果。
6. 静态通过、入口冒烟、性能通过分别记载；历史结果不得推广到其他配置、镜像或负载。

## NOTES.md 固定结构

```markdown
# 模型 / 部署方案 / 配置

## 1. 配置概况
模型、方案、配置标识、来源、配套镜像（未知则待确认）。

## 2. 服务实例与参数
脚本、角色、DP/TP/PCP、connector、DSpark、eager/graph、EPLB 与主要差异。
未显式设置的参数不推断默认值。

## 3. 现场绑定与依赖
IP、网卡、权重、HTTP/RPC/KV 端口、工作目录、挂载及环境脚本。

## 4. Proxy
实现来源/版本或摘要、启动脚本、后端 HTTP 端点组织、显式策略。
镜像是否自带文件未核验时必须标明。

## 5. 执行顺序
容器与环境准备、模型启动、健康检查、代理、冒烟、测试与释放。

## 6. 检查与验证状态
静态检查依据、未决项、真实验证时间/任务/负载/镜像、证据位置。

## 7. 原始记录与差异
原始输入来源、经确认的调整、历史记录入口。
```

## Proxy 与历史材料

当前公共代理目标为 `load_balance_proxy_server_example.py`，按源码版本/摘要识别，不按模型重新发明代理。现有目录中的不同源码版本暂不合并，以免改变相对路径和协议行为。以后引入公共版本时，需同步调整引用并做差异审阅。

`_retired`、`_ascend_runs` 和 `references` 不列入可执行配置矩阵。保留运行证据，不自动清理或把历史结果当作当前验证。
