## 工作方式

接受用户直接描述服务器、部署形式及对应测试需求，Agent 负责标准化为内部 case。单 case 是执行和管理单元，不作为首次对话限制；不要求用户理解 Schema 或先拆分任务。首次回复只询问实际缺项，不附加默认规则、工具检查职责或通用能力边界说明。具体需求出现歧义或能力缺口时，在承诺执行前说明。

1. 使用 [信息收集模板](references/intake-handoff.md)。本地脚本、远程脚本或粘贴内容只是输入来源；读取并审阅后提取命令、环境与部署参数，不把源脚本路径作为执行依赖。不盲目复制旧机器的权重位置、IP、网卡和端口。
2. 按 [任务配置与现场绑定](references/job-spec-review.md) 形成 job_spec v3。部署按实例和连接关系分层，case 独立定义，sub_tasks 明确引用部署和 case 并固定串行顺序；默认请求数由并发×4计算并显式保存，用户覆盖值优先。配置存储暂只记录事件，不实现配置库、版本检索或自动选配。
3. 完成有人值守阶段的现场预检与参数绑定后启动生成的串行任务入口。每个 sub_task 都经过 deploy → evaluate → finalize，deploy 依据当前服务状态决定复用或启动。未经确认不调小负载或改变部署参数。

## 五阶段与生成入口

规划可在本地完成，随后将完整任务目录传到 Linux 协调端，并将同一版本 Skill 包上传到各执行节点；协调端通过免密 SSH 调用固定节点脚本。现场路径绑定和执行在对应节点进行。本地任务目录及日志必须放在代码仓库之外。以 [任务示例](examples/job_spec.serial.json) 的结构填写实际需求，不能直接把示例负载当作授权。

```sh
python3 scripts/plan_run.py --job-spec /input/job_spec.json --run-dir /work/JOB_ID
# 将任务包上传到目标机；生成脚本使用包内快照。
python3 /work/JOB_ID/skill-snapshot/scripts/preflight.py --run-dir /work/JOB_ID --bindings /input/bindings.json
# 前台入口；Agent 后台提交方式见 references/task-monitoring.md
bash /work/JOB_ID/run.sh
# 需要独立收尾时：
python3 /work/JOB_ID/skill-snapshot/scripts/finalize.py --run-dir /work/JOB_ID
```

- **plan_run**：校验并冻结标准任务、计算默认值、保存 sub_task 顺序和执行代码快照，生成 run.sh。计划阶段允许现场位置尚未绑定；draft 或未决测试目标不进入可执行计划。
- **preflight**：在有人值守阶段解析现场信息，检查镜像、模型、挂载、网络、设备与工具。动态发现镜像内 AISBench 工作路径，分配不重叠端口范围，并生成 resolved-cluster.json 及各节点的最终启动脚本与 resolved.json。默认从已启用且有可用 IPv4 的接口中选择协商链路速率最高者，排除容器桥接等接口；速率未知、并列或多个地址时由 Agent 核验，不写死网卡名。绑定完成前 run.sh 拒绝启动。
- **deploy**：循环每轮均调用。有效 READY 服务跳过部署和冒烟；需要启动时再次检查即时资源，创建本任务容器，执行已审阅的启动命令并等待健康检查。默认冒烟仅一次 curl 非流式真实推理，保存请求、响应及服务身份。
- **evaluate**：每次执行一个标准 case，默认先重置缓存再按目标预热；从该 case 生成负载和配置，核验原始请求、输出长度及独立的实测前缀指标。客户端在结束或异常时清理，尝试与结果按 case 分别记录。
- **finalize**：每个 case 核验客户端/临时链接释放并应用服务策略；整组任务结束另做任务级收尾，逐个处理已登记部署的全部节点，即使某一释放失败也检查其他部署。释放失败单独报告，不能被测量通过覆盖。

run.sh 启动串行拓扑协调器。相同部署的连续子任务默认保留服务；切换部署默认只停止旧服务并复用兼容容器。每台机器的首个任务容器直接以总 job_id 命名；镜像或容器配置不兼容时才增加数字子编号容器。预检汇总所需权重挂载和设备，实例不再指定 container_group。探测容器用 -000 临时编号，检查后删除。任务结束默认停止并删除全部本任务容器，产物写在宿主挂载目录。节点操作核验归属及脚本摘要，整套服务必须所有节点健康且入口冒烟通过才 READY。

## Agent 提交与主动上报

实际提交任务时遵循 [任务监控](references/task-monitoring.md)：Agent 确认远端执行器独立于 SSH 会话运行后，绑定当前聊天定时监控，默认每5分钟检查；正常运行保持安静，仅在完成、失败或需要人工处理时上报。监控读取现有结果和释放证据，不重新执行任务或自动修复。无法建立监控时明确说明，不能承诺稍后主动通知。应用监控信息保存在仓库外运行记录，不加入 job_spec，也不交给五阶段脚本管理。用户只讨论设计、审阅提交或手工执行时，不自动创建监控。

## 状态、重试与资源

见 [生命周期](references/service-lifecycle.md)。服务身份和部署摘要与 case 负载分离；修改并发不影响部署身份。容器级锁保护各执行单元，任务锁保护整个循环。case 重试预算相互独立，默认最多额外3次；sub_tasks 的 on_failure 默认 record_only：失败记录后检查服务，健康则继续，确认退出并释放后让下个子任务重新部署；传输/身份不明或清理未核验时阻塞后续子任务并收尾；不自动重放未知状态。部署重建使用新的服务尝试预算并保留历史。

case 收尾将缓存标为待重置，下一 case 预热前实际重置并核验；首次 case 也执行重置。需要清理的模型进程启用 VLLM_SERVER_DEV_MODE=1；先确认各实例无运行/等待请求，再逐个直连 P/D 实例重置，全部返回 success=true 后才预热。失败使用现有 case 重试预算，详见生命周期。任务停止服务后不再多做缓存重置。归属不明、客户端清理未核验或中断状态未知时阻塞相关操作，执行适用的任务收尾，不盲目恢复。

## 边界与产物

当前工具适配器为 aisbench_prefix，工具源码及必要数据随包存放在 assets/aisbench-prefix；每个 attempt 复制并应用已验证的退出码/指标记录适配。仅接受 job_spec v3，部署来自规范化命令与现场绑定，不加载旧 recipe。PD 代理与许可证放在 assets/pd-proxy。未知启动配置仍需有人值守审阅，不自动把任意 shell 脚本完整转译为安全命令。

Agent 使用现有连接完成包上传，执行器通过 SSH 调用固定节点脚本。当前 PD 支持一个 P、一个 D、一个 proxy；精度、phase 并行屏障、多 P/D 拓扑、复杂中断恢复未实现。当前配置存储仅有 logs/config-storage-events.jsonl 埋点，记录标准化、绑定、部署验证和 case 结束，不建立配置数据库或检索服务。

保留计划、现场绑定、脚本快照、阶段/状态日志、每个 case 的原始结果和释放记录。只操作本任务资源，保留共享镜像与权重。自动流程的归档要求不强加给手动操作。docs 只放设计与工程计划；本地产物在仓库外，本机使用 D:/autobenchmark-local/。

仓库示例只用占位主机、镜像和模型位置，不写入实际服务器地址、镜像摘要、账号或私有资源路径；真实现场绑定只保存在仓库外任务产物。
